## Start a Task

Just describe what you need. The Orchestrator handles the rest: context gathering, complexity classification, planning, delegation, and verification.

```text
"Add a rate limiter to the API gateway"
"Find out why the login flow fails on iOS Safari"
"Review the auth module for security issues"
```

## Complexity at a Glance

| Complexity  | When                                              | What You See                                                      |
| ----------- | ------------------------------------------------- | ----------------------------------------------------------------- |
| **TRIVIAL** | Typo fix, rename, one-shot command                | In-memory DAG and generated `execution_id`; no plan artifacts     |
| **LOW**     | Small, reversible, single-domain work             | Ephemeral DAG through the shared execution loop                   |
| **MEDIUM**  | Multiple dependent files, components, or agents   | Persistent planner-confirmed DAG and one standard plan review     |
| **HIGH**    | Architecture, API/schema/auth, migration, or risk | Persistent DAG, high or critic plan review, risk-triggered checks |

## Complex Plans Are Resumable

New MEDIUM/HIGH tasks get a generated persistent plan ID and fresh `plan.yaml`.
TRIVIAL/LOW tasks use only an ephemeral `execution_id`; they do not create or
read plan artifacts.

MEDIUM/HIGH tasks produce durable plan artifacts:

```text
docs/plan/{plan_id}/
  plan.yaml              # Task breakdown plus plan-level context fields
```

Note: Task results are returned as minimal, role-specific JSON by each specialist agent; they are not persisted as separate files. Detailed evidence remains in task-scoped artifacts. Reusable context is initialized in `plan.yaml`; only compact, actionable evidence is relayed to dependent tasks through their handoff.

You can pause mid-work and resume later only with the exact plan ID:

```text
continue plan 20260714-api-rate-limiter
```

Do not use fuzzy names or partial IDs. Continuation and extension require the
exact persistent plan ID.

## After Successful Work

Gem Team can promote stable, reusable knowledge after final success. Promotion
is confidence-gated; task-local details stay in execution state.

- **Product decisions** -> `docs/PRD.yaml`
- **Technical conventions** -> `AGENTS.md`
- **Patterns & gotchas** -> Memory (repo/session/global)
- **Repeatable workflows** -> `.apm/skills/` (as `SKILL.md` playbooks; compiled into each target tool by APM)

## Practical Tips

- **Be specific**: clearer input -> better plans. Include error messages, file paths, and expected behavior.
- **Check plan artifacts** for MEDIUM/HIGH tasks: they show the full breakdown before execution starts.
- **Use plan IDs** to resume or extend MEDIUM/HIGH work across sessions.
- **Keep `apm_modules/` in `.gitignore`**: it's an install cache, not project code.
