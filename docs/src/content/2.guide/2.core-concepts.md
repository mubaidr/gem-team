## How It Works

The delivery pipeline covers task classification, planning, delegation, verification, debugging, and learning. Work is batched, dependencies are serialized, and high-confidence learnings are retained.

## Knowledge Layers

Gem Team organizes knowledge across six layers, each with a specific purpose:

| Layer              | Location                         | Purpose                                                                                                                             |
| :----------------- | :------------------------------- | :---------------------------------------------------------------------------------------------------------------------------------- |
| **PRD**            | `docs/PRD.yaml`                  | Product requirements, decisions, personas, business goals, success metrics, risks, and prioritization per Atlassian agile practices |
| **AGENTS.md**      | `AGENTS.md`                      | Stable project conventions, constitutional rules (e.g. Library-first), and agent instructions                                       |
| **Plan artifacts** | `docs/plan/{plan_id}/`           | Resumable task DAGs, status, minimal outputs, and task-scoped evidence                                                              |
| **Memory**         | Memory tool / configured backend | Durable facts, decisions, gotchas, patterns, and failure modes                                                                      |
| **Skills**         | `.apm/skills/`                   | Reusable procedures and domain guidance packaged as `SKILL.md` playbooks                                                            |
| **Derived docs**   | `docs/knowledge/`                | Reference notes, external docs, summaries, and research outputs                                                                     |

Plan artifacts store execution state, not project knowledge. `AGENTS.md` and repo memory hold stable knowledge, not task status or temporary assumptions. A new plan starts fresh and never inherits another plan automatically.

### Scoped Handoffs

Execution scope uses `task_definition.handoff`. The planner receives a bounded contract with the objective, acceptance criteria, risk signals, and only the clarifications and discovery needed to build the DAG. The reviewer receives a
dedicated review contract. Every delegate receives canonical handoff data plus a sanitized, role-scoped `config_snapshot`.

### Three-Tier Memory

| Tier        | Scope               | Persistence                     |
| :---------- | :------------------ | :------------------------------ |
| **Repo**    | Workspace-scoped    | Stored with the repository      |
| **Session** | Conversation-scoped | Cleared after conversation ends |
| **Global**  | User-scoped         | Persists across all workspaces  |

Only stable, reusable learnings with confidence at least 0.95 are promoted after final success; task-local evidence remains in session or execution state.

## Execution Model

All planned and executable work uses one DAG-based wave loop. Waves are the authoritative execution boundaries; `depends_on` records earlier-wave prerequisites and handoff evidence rather than competing with wave scheduling. Standalone research uses a direct read-only path without plan or execution artifacts. Complexity changes persistence, planner use, and review depth: TRIVIAL/LOW stays ephemeral, while MEDIUM/HIGH uses a persistent planner-confirmed plan. Routine MEDIUM plans pass deterministic validation without an extra reviewer call; independent review remains risk-adaptive. See [Workflow ->](/guide/workflow) for the full pipeline.
