## How It Works

Gem Team wraps your AI with a structured delivery pipeline: task classification, planning, delegation, verification, debugging, and learning: so you get reliable results without depending on a single long prompt.

Work is batched, dependencies are serialized, and high-confidence learnings are saved for future runs.

## Knowledge Layers

Gem Team organizes knowledge across six layers, each with a specific purpose:

| Layer              | Location                         | Purpose                                                                                                                             |
| :----------------- | :------------------------------- | :---------------------------------------------------------------------------------------------------------------------------------- |
| **PRD**            | `docs/PRD.yaml`                  | Product requirements, decisions, personas, business goals, success metrics, risks, and prioritization per Atlassian agile practices |
| **AGENTS.md**      | `AGENTS.md`                      | Stable project conventions, constitutional rules (e.g. Library-first), and agent instructions                                       |
| **Plan artifacts** | `docs/plan/{plan_id}/`           | Per-task plans, plan context, task registries, evidence, and results                                                                |
| **Memory**         | Memory tool / configured backend | Durable facts, decisions, gotchas, patterns, and failure modes                                                                      |
| **Skills**         | `.apm/skills/`                   | Reusable procedures and domain guidance packaged as `SKILL.md` playbooks                                                            |
| **Derived docs**   | `docs/knowledge/`                | Reference notes, external docs, summaries, and research outputs                                                                     |

Plan artifacts and plan context are plan-scoped execution state. `AGENTS.md` and reusable repo memory hold stable repository knowledge; they are not alternate stores for task status, wave outputs, or temporary assumptions. A new plan starts with fresh artifacts and does not inherit another plan automatically.

### Plan Context

Plan context is stored directly in the existing plan schema as top-level context fields and is initialized once for the plan. It changes only through an explicit replan. Task scope is passed to agents via `task_definition.handoff`, never as a separate plan payload. Plan-level fields include:

- **Tech stack**: languages, frameworks, libraries, and versions
- **Architecture snapshot**: component relationships, data flow, API contracts
- **Conventions**: coding style, naming, patterns, testing approach
- **Constraints**: platform, performance, security, accessibility requirements
- **Research digest**: findings from codebase exploration
- **Prior decisions**: architectural and design decisions with rationale

Plan context is not refreshed after each execution wave; relevant intermediate learnings are relayed only to dependent tasks through `handoff`. Existing plan context is used only when the user explicitly names that plan as a reference; imported facts must be revalidated and source-attributed. Legacy plans with a separate context file are migrated once on exact resume, then `plan.yaml` is authoritative.

Task-specific execution context is passed through the canonical `handoff` field. The orchestrator includes it in every downstream task payload. Agents use only the fields relevant to their role: scope limits, target files, test-first requirements, minimal-change guidance, and acceptance checks.

### Three-Tier Memory

| Tier        | Scope               | Persistence                     |
| :---------- | :------------------ | :------------------------------ |
| **Repo**    | Workspace-scoped    | Stored with the repository      |
| **Session** | Conversation-scoped | Cleared after conversation ends |
| **Global**  | User-scoped         | Persists across all workspaces  |

Facts are persisted only when confidence ≥ 0.85, with high-confidence items (≥ 0.90, stable, ≥ 3 uses) promoted to durable cache. Auto-eviction occurs after 90 days with no access (read or write).
