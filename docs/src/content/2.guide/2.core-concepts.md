## How It Works

The delivery pipeline covers task classification, planning, delegation, verification, debugging, and learning. Work is batched, dependencies are serialized, and high-confidence learnings are retained.

## Knowledge Layers

Gem Team organizes knowledge across six layers, each with a specific purpose:

| Layer              | Location                         | Purpose                                                                                                                             |
| :----------------- | :------------------------------- | :---------------------------------------------------------------------------------------------------------------------------------- |
| **PRD**            | `docs/PRD.yaml`                  | Product requirements, decisions, personas, business goals, success metrics, risks, and prioritization per Atlassian agile practices |
| **AGENTS.md**      | `AGENTS.md`                      | Stable project conventions, constitutional rules (e.g. Library-first), and agent instructions                                       |
| **Plan artifacts** | `docs/plan/{plan_id}/`           | Per-task plans, plan context, task registries, evidence, and results                                                                |
| **Memory**         | Memory tool / configured backend | Durable facts, decisions, gotchas, patterns, and failure modes                                                                      |
| **Skills**         | `.apm/skills/`                   | Reusable procedures and domain guidance packaged as `SKILL.md` playbooks                                                            |
| **Derived docs**   | `docs/knowledge/`                | Reference notes, external docs, summaries, and research outputs                                                                     |

Plan artifacts are plan-scoped. `AGENTS.md` and repo memory hold stable knowledge, not task status or temporary assumptions. A new plan starts fresh and never inherits another plan automatically.

### Plan Context

Plan context is initialized once for a persistent MEDIUM/HIGH plan and changes only through an explicit replan. Execution scope uses `task_definition.handoff`; planner and reviewer use dedicated handoff contracts. Plan-level fields include:

- **Tech stack**: languages, frameworks, libraries, and versions
- **Architecture snapshot**: component relationships, data flow, API contracts
- **Conventions**: coding style, naming, patterns, testing approach
- **Constraints**: platform, performance, security, accessibility requirements
- **Research digest**: findings from codebase exploration
- **Prior decisions**: architectural and design decisions with rationale

Plan context is not refreshed after each wave. Only compact evidence needed by dependent tasks is relayed through `handoff`. Referenced plan context must be revalidated and source-attributed; legacy context files migrate once on exact resume.

Every delegate receives canonical handoff data plus a sanitized, role-scoped `config_snapshot`.

### Three-Tier Memory

| Tier        | Scope               | Persistence                     |
| :---------- | :------------------ | :------------------------------ |
| **Repo**    | Workspace-scoped    | Stored with the repository      |
| **Session** | Conversation-scoped | Cleared after conversation ends |
| **Global**  | User-scoped         | Persists across all workspaces  |

Only stable, reusable learnings with confidence at least 0.95 are promoted after final success; task-local evidence remains in session or execution state.

## Execution Model

All executable work uses one DAG-based wave loop. Complexity changes persistence, planner use, and review depth: TRIVIAL/LOW stays ephemeral, while MEDIUM/HIGH uses a persistent planner-confirmed plan and one pre-execution review. See [Workflow ->](/guide/workflow) for the full pipeline.
