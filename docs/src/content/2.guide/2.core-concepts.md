## How It Works

The delivery pipeline covers task classification, planning, delegation, verification, debugging, and learning. Work is batched into ordered waves, and high-confidence learnings are retained.

## Knowledge Layers

Gem Team organizes knowledge across six layers, each with a specific purpose:

| Layer              | Location                         | Purpose                                                                                                                             |
| :----------------- | :------------------------------- | :---------------------------------------------------------------------------------------------------------------------------------- |
| **PRD**            | `docs/PRD.yaml`                  | Product requirements, decisions, personas, business goals, success metrics, risks, and prioritization per Atlassian agile practices |
| **AGENTS.md**      | `AGENTS.md`                      | Stable project conventions, constitutional rules (e.g. Library-first), and agent instructions                                       |
| **Plan artifacts** | `docs/plan/{plan_id}/`           | Resumable wave plans, status, minimal outputs, and task-scoped evidence                                                             |
| **Memory**         | Memory tool / configured backend | Durable facts, decisions, gotchas, patterns, and failure modes                                                                      |
| **Skills**         | `.apm/skills/`                   | Reusable procedures and domain guidance packaged as `SKILL.md` playbooks                                                            |
| **Derived docs**   | `docs/knowledge/`                | Reference notes, external docs, summaries, and research outputs                                                                     |

Plan artifacts store execution state, not project knowledge. `AGENTS.md` and repo memory hold stable knowledge, not task status or temporary assumptions. A new plan starts fresh and never inherits another plan automatically.

### Scoped Handoffs

Execution scope uses `task_definition.handoff`. The Orchestrator passes the Planner a bounded `planning_context` with the objective, acceptance criteria, risk signals, and only the clarifications and discovery needed to build the ordered waves. The Planner returns `plan.yaml`; the Orchestrator then derives per-task execution handoffs with constraints, target files, prior-wave outputs, and runtime evidence. The reviewer receives a dedicated review `handoff`. Every delegate receives a sanitized, role-scoped `config_snapshot`.

### Three-Tier Memory

| Tier        | Scope               | Persistence                     |
| :---------- | :------------------ | :------------------------------ |
| **Repo**    | Workspace-scoped    | Stored with the repository      |
| **Session** | Conversation-scoped | Cleared after conversation ends |
| **Global**  | User-scoped         | Persists across all workspaces  |

Only stable, reusable learnings with confidence at least 0.95 are promoted after final success; task-local evidence remains in session or execution state.

## Execution Model

All planned and executable work uses one wave loop. Each wave completes before the next begins; task-scoped execution handoffs carry the evidence needed by later waves. A single bounded, low-risk task uses the direct specialist fast path. Other TRIVIAL/LOW work stays ephemeral, while MEDIUM/HIGH uses a persistent planner-confirmed plan. Routine MEDIUM plans pass deterministic validation without an extra reviewer call; review remains required for HIGH complexity, high-risk or critic signals, explicit requests, or insufficient or contradictory evidence.
