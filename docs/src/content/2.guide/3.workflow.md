Gem Team turns AI coding into a structured process. The Orchestrator runs a 5-phase pipeline: **Init -> Route -> Plan -> Execute -> Output**, with **Learn & Persist** between waves. Each phase adapts to task complexity: simple fixes get a quick checklist, complex features get full planning and review.

## Phase 0: Init & Clarify

The Orchestrator assesses every incoming request:

1. **Read context**: external references, errors, user config (`.gem-team.yaml`), relevant memory.
2. **Detect intent**: feature, bug-fix, refactor, docs, research, or debug.
3. **Resolve plan state** using the exact-ID decision table below.
4. **Classify complexity**: intent-based defaults (bug-fix -> LOW, research -> LOW), with explicit user overrides. Full classification kicks in only when intent is ambiguous.
5. **Document gray areas**: assumptions logged; only blocking ambiguities prompt the user.

### Plan identity and context isolation

Plan selection is explicit and exact. A new task never inherits another plan's files or context cache.

- `new_task` -> new plan ID; create fresh `plan.yaml` with fresh top-level plan context fields.
- `resume` -> requires an exact explicit `plan_id`; load only that plan.
- Missing/invalid `plan_id` -> escalate; no fuzzy matching or silent replacement.
- Explicit `derive` -> still `new_task`; import only revalidated, source-attributed facts.

> **Outcome**: A clear complexity classification and plan state that drives everything downstream.

## Phase 1: Route

Routes based on plan state:

| State                         | Action                                                  |
| ----------------------------- | ------------------------------------------------------- |
| `continue_plan` + no feedback | Load only the exact plan -> jump to Phase 3 Execution   |
| `continue_plan` + feedback    | Load only the exact plan -> Phase 2 Planning (revision) |
| `new_task`                    | Fresh plan and context -> Phase 2 Planning              |

## Phase 2: Planning

Planning depth matches complexity:

- **TRIVIAL/LOW**: Orchestrator creates a minimal ephemeral plan (direct task checklist). Bug-fix tasks route to `gem-debugger` first, then `gem-implementer`.
- **MEDIUM**: Delegates to `gem-planner` for lean DAG decomposition, wave scheduling, and risk-based planning. Standard reviewer validation applies to meaningful dependency, contract, security, shared-state, or explicit review risk.
- **HIGH**: Uses high reviewer validation unless a critic signal is present. Architecture, breaking-change, and cross-domain plans use one in-plan critic task instead of a second high review.

### Reviewer and critic routing

`gem-reviewer` supports `plan`, `wave`, and `critic` review modes. Plan review
uses `standard` or `high` depth. The Orchestrator selects exactly one level:
standard for medium-risk plans, high for high-risk plans, and critic for
architecture, breaking-change, or cross-domain signals. Critic replaces high
review and runs as one wave-1 task in complex plans. The Orchestrator also
routes four non-implementation intents to the reviewer in critic mode:

- `discuss`: examine an idea or decision.
- `proposal`: challenge a proposed approach.
- `feature_idea`: test a feature idea before implementation.
- `challenge`: perform a critical challenge of assumptions and blockers.

Critic mode is read-only. It does not implement the proposal, mutate files, or
claim that proposed work is complete. Its output keeps the common reviewer
fields and adds a structured `critic_verdict`, plus `challenges`,
`alternatives`, and `decision_blockers`. Each reported record must include
evidence, impact, and a concrete action. Existing `plan` and `wave` callers do
not require critic-only input or output fields.

Critic mode requires the following input contract. The field names are exact;
do not replace them with aliases:

```yaml
critic_subject:
  objective: string
  proposal: string
  constraints: string[]
  alternatives: string[]
  evidence: string[]
  decision_needed: string
critic_context:
  audience: string
  time_horizon: string
  success_criteria: string[]
  known_unknowns: string[]
```

> **Validation failure**: Replan with findings within the bounded replan budget, or escalate to the user when the
> budget is exhausted, progress is not measurable, or the objective/acceptance criteria would change.

### Replan guardrails

Replans revise execution details, not the user's goal:

- Each plan captures an immutable baseline objective and acceptance-criteria set.
- Replans use explicit lineage (`revision`, `replan_count`, `max_replans`); the default maximum is two.
- Every replan must name its reason, changed/added/removed tasks, preserved criteria, new risks, and measurable progress.
- Empty or repetitive replans stop and escalate instead of looping.
- Changed dependencies or criteria invalidate affected completed-task results and stale wave snapshots.
- `needs_revision` is routed by source: plan review gets a bounded planner revision; execution retries are capped, then escalate.

## Phase 3: Execution

Work runs in **waves**: groups of parallel tasks respecting dependency ordering:

1. **Wave collection**: tasks with `status=pending`, `wave=current`, all deps met.
2. **Conflict prevention**: tasks listed in `conflicts_with` never run in parallel.
3. **Delegation**: each task goes to its assigned specialist agent with its `task_definition` (authoritative scope) and `config_snapshot`.
   Task-specific boundaries and verification checks are passed through the task's canonical `handoff` field. Every downstream agent receives it and must apply the fields relevant to its role.
4. **Integration gates**: verify every wave's acceptance criteria. Invoke `gem-reviewer` only when wave or final-scope risk requires it:
   - security-sensitive, public-contract, migration, shared-state, irreversible, cross-domain, conflict, or explicit review risk;
   - otherwise deterministic task evidence is sufficient for low-risk work.
5. **State**: persist task status and the minimal agent output needed for orchestration. Keep context stable between waves; relay only compact, actionable evidence to dependent tasks.
6. **Evidence & Persist**: keep detailed evidence in task-scoped paths and pass only paths or manifests. Durable knowledge is opt-in and is promoted only when explicitly requested and confidence is at least 0.95. Reusable workflows belong in `.apm/skills/` as `SKILL.md` files.

> Plans are **resumable**: pause, inspect, and continue only with the exact plan ID. To use another plan for context, explicitly name it as a reference; the current task still starts with fresh artifacts.

### Wave Example

```text
Wave 1: [Debugger] diagnose error
                   ↓
Wave 2: [Implementer] fix + [Tester] verify
                   ↓
Wave 3: [Reviewer] integration + security check
```

## Phase 4: Output

Structured status report with:

- Plan ID and objective · Task progress (completed/total, %)
- Wave status · Blocked tasks with reasons · Next steps

### Agent output policy

Agent results use the smallest role-specific schema that preserves workflow state and required
handoffs. Results must not repeat input fields, plan criteria, workflow instructions, or analysis
that no downstream task consumes. Optional fields are omitted when empty. Detailed evidence stays in
task-scoped artifacts and is referenced by a path or manifest. There is no universal `learn` or
per-criterion acceptance-result field.
