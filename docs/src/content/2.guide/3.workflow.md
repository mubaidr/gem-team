The Orchestrator runs a five-phase pipeline: **Init -> Route -> Plan -> Execute -> Output**. Every task uses the same DAG loop; complexity controls persistence and review depth.

## Phase 0: Init & Clarify

Phase 0 performs a shallow, non-delegable classification:

1. Load `.gem-team.yaml`, when present, and only memory needed for continuity.
2. Normalize `request_state` (`new_task`, `continue_plan`, or `extend`) and intent (`execute`, `debug`, `research`, `discuss`, or `challenge`) plus only intent-required fields.
3. Match explicit or strongly implied risk signals from supplied evidence. Do not inspect the repository or delegate to improve confidence.
4. Assign provisional complexity once: TRIVIAL for one bounded no-runtime change, LOW for small reversible single-domain work, MEDIUM for multiple dependent files/components/agents, and HIGH for a matched high-risk signal.
5. Ask only about a decision blocker; otherwise record one bounded assumption and route immediately.

### Plan identity and state isolation

Plan selection is explicit and exact. A new task never inherits another plan's execution state.

- `new_task` -> route by provisional complexity; generate a persistent `plan_id` only for MEDIUM/HIGH.
- `continue_plan` or `extend` -> require an exact explicit `plan_id`; never infer or fuzzy-match one.
- Missing or invalid required `plan_id` -> block and request it.
- TRIVIAL/LOW -> use only a generated `execution_id`; never access plan artifacts.

## Phase 1: Route

Routes based on plan state:

| State                                            | Action                                    |
| ------------------------------------------------ | ----------------------------------------- |
| `discuss`                                        | Answer directly in Phase 4                |
| `challenge`                                      | Run read-only critic review, then Phase 4 |
| `continue_plan` + no/execution-only feedback     | Phase 3 Execution                         |
| `continue_plan` + scope/dependency/criteria edit | Phase 2 Planning                          |
| `new_task` or valid `extend`                     | Phase 2 Planning                          |

## Phase 2: Planning

Planning depth matches complexity:

- **TRIVIAL/LOW**: The Orchestrator creates an in-memory DAG using the persistent task shape, but does not call the planner or reviewer. Bug-fix work routes to `gem-debugger` before `gem-implementer`.
- **MEDIUM/HIGH**: Generate or reuse the exact persistent `plan_id`, then delegate to `gem-planner`. The planner confirms MEDIUM/HIGH complexity, may promote it, and never downgrades it.
- **Pre-execution review**: Every MEDIUM/HIGH plan receives exactly one full plan review: standard for MEDIUM, high for HIGH/high-risk, or critic for architecture, breaking-change, or cross-domain signals.

### Reviewer and critic routing

Reviewer routing uses three independent axes:

- `review_mode`: `standard`, `high`, or `critic` controls intensity.
- `review_target`: `plan`, `task`, `code`, `decision`, `docs`, `config`, or `integration` selects the artifact.
- `review_scope`: `changed`, `affected`, or `full` limits evidence breadth.

Discussion bypasses delegation. Only a requested evaluation or decision routes
as `challenge`, with critic mode, decision target, and full scope. Critic mode
is read-only: it does not implement proposals, mutate files, or claim
completion. Critic fields live under the reviewer handoff:

```yaml
review_mode: critic
review_target: decision
review_scope: full
handoff:
  critic_subject:
    objective: string
    proposal: string
    constraints: string[]
    alternatives: string[]
    evidence: string[]
    decision_needed: string
  critic_context:
    audience: string
    time_horizon: string
    success_criteria: string[]
    known_unknowns: string[]
```

Validation failures trigger a bounded replan or escalation when the budget is exhausted, progress is not measurable, or the objective or criteria would change.

### Replan guardrails

Replans revise execution details, not the user's goal:

- Each plan captures an immutable baseline objective and acceptance-criteria set.
- Replans use explicit lineage (`revision`, `replan_count`); the default maximum is two.
- Every replan must name its reason, changed/added/removed tasks, preserved criteria, new risks, and measurable progress.
- Replans pass the immutable baseline, the exact current plan, and concrete findings back to the planner. The planner may revise DAG structure, routing, dependencies, and waves, but may not change the baseline or decide whether the replan budget is exhausted.
- Empty or repetitive replans stop and escalate instead of looping.
- Changed dependencies or criteria invalidate affected completed-task results and stale wave snapshots.
- `needs_revision` is routed by source: plan review gets a bounded planner revision; execution retries are capped, then escalate.

## Phase 3: Execution

All complexity levels use one wave-based DAG loop. TRIVIAL/LOW uses an `execution_id`; MEDIUM/HIGH persists under the exact `plan_id` and `plan.yaml`.

1. **Wave collection**: load the lowest pending wave and its direct dependencies; select tasks whose dependencies are complete.
2. **Conflict prevention**: tasks listed in `conflicts_with` never run in parallel.
3. **Delegation**: each execution task goes only to its assigned specialist with `execution_id`, optional persistent `plan_id`, authoritative `task_definition`, and a role-scoped `config_snapshot`. Every execution `task_definition` contains `objective`, `acceptance_criteria`, and canonical `handoff`; constraints, target files, dependency outputs, findings, and runtime evidence stay in that handoff. Planner and reviewer use dedicated contracts.
4. **Integration gates**: verify every task and the final aggregate acceptance criteria. Invoke `gem-reviewer` only for security-sensitive, public-contract, migration, shared-state, irreversible, cross-domain, or explicit changed-scope risk. Otherwise, deterministic task evidence is sufficient.
5. **State**: update ephemeral state in memory or persist task status and minimal output to `plan.yaml`. Relay only compact, actionable evidence to dependent tasks.
6. **Evidence & persist**: keep detailed evidence in task-scoped paths and pass paths or manifests. Promote durable knowledge only when requested and confidence is at least 0.95; reusable workflows belong in `.apm/skills/`.

> Persistent plans are resumable only by exact plan ID. Ephemeral execution never reads plan artifacts.

### Wave Example

```text
Wave 1: [Debugger] diagnose error
                   ↓
Wave 2: [Implementer] fix + [Tester] verify
                   ↓
Final gate: [Reviewer] only when integration risk is triggered
```

## Phase 4: Output

Return a structured report with:

- Execution ID, optional plan ID, and objective · Task progress (completed/total, %)
- Wave status · Blocked tasks with reasons · Next steps

### Agent output policy

Agent results use the smallest role-specific schema that preserves workflow state and required
handoffs. Results must not repeat input fields, plan criteria, workflow instructions, or analysis
that no downstream task consumes. Optional fields are omitted when empty. Detailed evidence stays in
task-scoped artifacts and is referenced by a path or manifest. There is no universal `learn` or
per-criterion acceptance-result field.
