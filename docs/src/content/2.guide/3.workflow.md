The Orchestrator runs a five-phase pipeline: **Init -> Route -> Plan -> Execute -> Output**. Planned and executable work uses ordered waves; standalone research uses a direct read-only fast path.

## Phase 0: Init & Clarify

Phase 0 performs a shallow, non-delegable classification:

1. Load `.gem-team.yaml`, when present, and only memory needed for continuity.
2. Assign or validate the exact `plan_id`, then normalize `request_state` (`new_task`, `continue_plan`, or `extend`) and intent (`execute`, `debug`, `research`, `discuss`, or `challenge`) plus only intent-required fields.
3. Match explicit or strongly implied risk signals from supplied evidence. Do not inspect the repository or delegate to improve confidence.
4. Assign provisional complexity once: TRIVIAL for one bounded no-runtime change, LOW for small reversible single-domain work, MEDIUM for multiple dependent files/components/agents, and HIGH for a matched high-risk signal.
5. Ask only about a decision blocker; otherwise record one bounded assumption and route immediately.

### Plan identity and state isolation

Plan selection is explicit and exact. A new task never inherits another plan's workflow state.

- `new_task` -> generate a new `plan_id` for correlation; persistent plans use it for MEDIUM/HIGH work.
- `continue_plan` or `extend` -> require an exact explicit `plan_id`; never infer or fuzzy-match one.
- Missing or invalid required `plan_id` -> block and request it.
- Every path has a `plan_id`. TRIVIAL/LOW uses it for correlation only and never accesses plan artifacts.

## Phase 1: Route

Routes based on plan state:

| State                                        | Action                                     |
| -------------------------------------------- | ------------------------------------------ |
| `discuss`                                    | Answer directly in Phase 4                 |
| `challenge`                                  | Run read-only critic review, then Phase 4  |
| `research`                                   | Direct `gem-researcher` call, then Phase 4 |
| `continue_plan` + no/execution-only feedback | Phase 3 Execution                          |
| `continue_plan` + scope/wave/criteria edit   | Phase 2 Planning                           |
| `new_task` or valid `extend`                 | Phase 2 Planning                           |

Standalone research uses its `plan_id` for correlation but does not create
persistent plan artifacts, workflow state, or a wave. The Orchestrator maps
the research question and expected deliverable into the research task
contract, validates the returned deliverable, and reports the findings
directly. If the researcher returns `next_action: plan_follow_up`, the
Orchestrator promotes complexity from the evidence and enters Phase 2 with the
findings as bounded planning context under the same `plan_id`.

> Fast-path work auto-promotes when continued execution needs dependencies, shared state, contract/risk changes, or durable evidence. Keep `plan_id`, create `docs/plan/{plan_id}/plan.yaml`, preserve valid work/acceptance criteria, and route remaining scope through the Planner.

## Phase 2: Planning

Planning depth matches complexity:

- **TRIVIAL/LOW**: A single bounded task with clear acceptance criteria, one owner, and no high-risk signal uses the direct specialist fast path. Other TRIVIAL/LOW work uses an in-memory wave plan without planner or reviewer calls. Bug-fix work routes to `gem-debugger` before `gem-implementer`.
- **MEDIUM/HIGH**: Generate or reuse the exact persistent `plan_id`, then delegate to `gem-planner`. The planner confirms MEDIUM/HIGH complexity, may promote it, and never downgrades it.
- **Pre-execution review**: Every MEDIUM/HIGH plan receives deterministic validation. Routine MEDIUM plans with no risk signals, no explicit review request, and sufficient consistent evidence proceed without an independent reviewer. Review is required for HIGH complexity, high-risk or critic signals, explicit review requests, or insufficient or contradictory evidence.

### Reviewer and critic routing

Reviewer routing uses three independent axes:

- `review_mode`: `standard`, `high`, or `critic` controls intensity.
- `review_target`: `plan`, `task`, `code`, `decision`, `docs`, `config`, or `integration` selects the artifact.
- `review_scope`: `changed`, `affected`, or `full` limits evidence breadth.

Discussion bypasses delegation. Only a requested evaluation or decision routes
as `challenge`, with critic mode, decision target, and full scope. Critic mode
is read-only: it does not implement proposals, mutate files, or claim
completion. Critic fields live under the reviewer handoff:

```yaml
review_mode: critic
review_target: decision
review_scope: full
handoff:
  critic_subject:
    objective: string
    proposal: string
    constraints: string[]
    alternatives: string[]
    evidence: string[]
    decision_needed: string
  critic_context:
    audience: string
    time_horizon: string
    success_criteria: string[]
    known_unknowns: string[]
```

Validation failures trigger a bounded replan or escalation when the budget is exhausted, progress is not measurable, or the objective or criteria would change.

### Replan guardrails

Replans revise execution details, not the user's goal:

- Each plan captures an immutable baseline objective and acceptance-criteria set.
- Replans use explicit lineage (`revision`, `replan_count`); the default maximum is two.
- Every replan must name its reason, changed/added/removed tasks, preserved criteria, new risks, and measurable progress.
- Replans pass the immutable baseline, the exact current plan, and concrete findings back to the planner as `planning_context`. The planner may revise wave structure, routing, task handoffs, and validation, but may not change the baseline or decide whether the replan budget is exhausted.
- Empty or repetitive replans stop and escalate instead of looping.
- Changed wave assignments, handoffs, or criteria invalidate affected completed-task results and stale wave snapshots.
- `needs_revision` is routed by source: plan review gets a bounded planner revision; execution retries are capped, then escalate.

## Phase 3: Execution

All planned and executable work uses one wave loop. Every workflow has a
`plan_id`; ephemeral paths use it for correlation only, while persistent paths
use `docs/plan/{plan_id}/`. Standalone research is read-only and does not use
persistent plan artifacts unless promoted to follow-up planning.

1. **Wave collection**: load the lowest incomplete wave. Waves are the authoritative execution boundary; do not advance while a lower wave remains incomplete. Select all pending tasks in that wave.
2. **Ownership safety**: tasks with overlapping ownership never run in parallel.
3. **Delegation**: each execution task goes only to its assigned specialist with `plan_id`, authoritative `task_definition`, and a role-scoped `config_snapshot`. Every `task_definition` contains `objective`, `acceptance_criteria`, and a nested `handoff`; constraints, target files, prior-wave outputs, findings, and runtime evidence stay in that handoff. Planner receives `planning_context`; reviewer uses a dedicated review `handoff`.
4. **Integration gates**: verify every task and the final aggregate acceptance criteria. Invoke `gem-reviewer` only when the review can change the decision: HIGH complexity, high-risk or critic signals, explicit review requests, or insufficient or contradictory evidence. Otherwise, deterministic task evidence is sufficient.
5. **State**: update ephemeral state in memory or persist task status and minimal output to `plan.yaml`. Relay only compact, actionable evidence to later-wave tasks.
6. **Evidence & persist**: keep detailed evidence in task-scoped paths and pass paths or manifests. Promote durable knowledge only when requested and confidence is at least 0.95; reusable workflows belong in `.apm/skills/`.

> Persistent plans are resumable only by exact plan ID. Ephemeral workflows never read plan artifacts.

### Wave Example

```text
Wave 1: [Debugger] diagnose error
                   ↓
Wave 2: [Implementer] fix + [Tester] verify
                   ↓
Final gate: [Reviewer] only when integration risk is triggered
```

## Phase 4: Output

Return a structured report with:

- Plan ID and objective · Task progress (completed/total, %)
- Wave status · Blocked tasks with reasons · Next steps

### Agent output policy

Agent results use the smallest role-specific schema that preserves workflow state and required handoffs (execution `task_definition.handoff` or review `handoff`). Results must not repeat input fields, plan criteria, workflow instructions, or analysis that no downstream task needs. Optional fields are omitted when empty. Detailed evidence stays in task-scoped artifacts and is referenced by a path or manifest. There is no universal `learn` or per-criterion acceptance-result field.
